# UI Studio Feature Checklist

Track implementation and review status for all 39 UI Studio features.
**Status key:** ✅ Done | ⬜ Pending

---

| # | Feature | What is implemented | Purpose / Usage | Status |
|---|---------|--------------------|--------------------|--------|
| 1 | **UI Studio navigation** | `/studio/views` list page and `/studio/views/:viewId/edit` designer route are wired into the app shell. | Gives designers one entry point to manage and edit UI views. | ✅ Done |
| 2 | **View registry** | Grid of UI views with view label/code, surface, primary entity, draft/published status, version, and modified time. Includes search, surface filter, status filter, row click edit, and archive action. | Used to find, open, create, and retire UI view definitions. | ✅ Done |
| 3 | **New view creation** | Modal captures view label, primary entity, surface type, and optional `view_code`. | Starts a new editable UI view draft tied to an entity and surface. | ✅ Done |
| 4 | **Surface type support** | Model supports `standard_crud`, `advanced_crud`, `header_line`, `custom_page`, `dashboard`, `wizard`, `detail_page`, `split_view`, `kanban`, and `calendar`. Runtime lookup can also resolve by `view_code` + `entity` + `surface`. | Classifies what kind of screen/workspace the view represents. | ✅ Done |
| 5 | **View designer shell** | Toolbar (view label, view_code badge, dirty indicator, undo/redo, save/publish/preview/settings). Left rail with Outline / Library / Fields tabs. Center ZoneCanvas (surface-aware zone cards, component blocks, drag-drop from palette and fields). Right panel always-visible (empty state + property panel). Component tree context menu (duplicate, delete, move up/down, wrap in section). | Main design-time workspace for building a view payload. | ✅ Done |
| 6 | **Component palette** | Searchable registry-driven component library grouped by category. Components can be dragged or double-clicked into the tree. | Lets users compose screens from registered UI building blocks. | ⬜ Pending |
| 7 | **Component registry** | 76 seeded platform components: 5 action, 7 composite, 2 container, 8 data, 16 display, 22 input, 12 layout, 4 navigation. Registry stores supported surfaces, bindings, schemas, defaults, event support, renderer names, and validation metadata. | Makes the designer extensible and data-driven instead of hardcoding every component in the UI. | ⬜ Pending |
| 8 | **Component tree editing** | Select, hover, insert, delete, duplicate, move support in Zustand store; root cannot be deleted. | Builds and maintains the nested view component hierarchy. | ⬜ Pending |
| 9 | **Placement guardrails** | Insert checks use registry rules for `allowed_parents`, `allowed_children`, and container status. | Prevents invalid component nesting while designing. | ⬜ Pending |
| 10 | **Undo/redo** | Store keeps up to 50 payload history entries; toolbar and keyboard shortcuts support undo/redo. | Lets designers recover from local editing mistakes. | ⬜ Pending |
| 11 | **Schema-driven properties** | Property panel generates controls from each component's `config_schema`: string, number, boolean, enum. | Allows configuring component props without writing JSON manually. | ⬜ Pending |
| 12 | **Field/data bindings** | Components can bind supported properties to entity fields, computed expressions, static values, or JSONata-style expressions. Entity fields are loaded for the view's primary entity. | Connects visual components to business/entity data. | ⬜ Pending |
| 13 | **Data source editor** | Multiple data sources per view with source key, base entity, filters, dynamic filter flag, sorting, joins, pagination, and infinite scroll flag. | Defines where view data should come from and how lists/grids should be filtered or shaped. | ⬜ Pending |
| 14 | **Event editor** | Component event handlers can be added with event type, active flag, priority, and actions. | Configures dynamic behavior like click handling, field updates, navigation, API calls, modal open/close, refresh, toast, validation, filters, and reset. | ⬜ Pending |
| 15 | **Event engine** | Pure TypeScript event engine supports sequential async action execution, condition evaluation, role/field context, errors, custom handlers, subscriptions, and shared dispatch helper. | Provides runtime behavior plumbing for component-to-component interactions. | ⬜ Pending |
| 16 | **Visibility rules** | Per-component rules: always visible, field equals, expression, or role-based; includes remove-from-DOM option. | Controls conditional display of UI elements. | ⬜ Pending |
| 17 | **Runtime context application** | Runtime helper applies visibility and permission rules to the tree, removing hidden nodes and marking read-only/required nodes. | Turns design metadata into runtime-ready component behavior. | ⬜ Pending |
| 18 | **Permission editor** | Selected component can store default access plus role overrides: full, read-only, hidden, and required. | Configures role-sensitive component behavior. | ⬜ Pending |
| 19 | **Validation rule editor** | UI supports required, min/max length, min/max value, pattern, email, URL, numeric, alpha, alphanumeric, date range, file size/type, and custom expression rules. Runtime helper currently executes the common text/number/pattern/email/URL rules. | Defines component-level input validation metadata. | ⬜ Pending |
| 20 | **Live preview** | Preview recursively renders the component tree, applies runtime context, highlights selected/conditional/read-only nodes, and wires button click events into the event engine. | Lets designers inspect a view before publishing. | ⬜ Pending |
| 21 | **Preview renderers** | Implemented renderers include page root, section, row/column, conditional container, toolbar, header-line, grid row/column, text/number/date/dropdown/reference/checkbox/textarea, label, badge, status badge, metric comparison, table, card grid, filter panel, totals panel, tax/charge, related list, modal, drawer, side panel, dashboard grid, wizard step, split panel, kanban board, and button. Some seeded components still fall back to a generic preview. | Gives visual feedback for most core view-building components. | ⬜ Pending |
| 22 | **Header-line workspace preview** | Header-line renderer separates children into Header and Line Grid zones; totals and tax/charge preview components exist. | Supports transaction-style screens such as sale/service orders. | ⬜ Pending |
| 23 | **Dashboard surface settings** | Dashboard editor configures columns, row height, gap, widget slots, row/column/width/height, and refresh interval. | Controls dashboard widget grid layout. | ⬜ Pending |
| 24 | **Wizard surface settings** | Wizard editor configures step list, ordering, labels, component mapping, optional steps, skip condition, validation expression, back navigation, step numbers, and completion action. | Builds guided multi-step entry flows. | ⬜ Pending |
| 25 | **Draft save** | Manual save and `Ctrl+S`; saves payload as a draft version. | Persists work-in-progress view configuration. | ⬜ Pending |
| 26 | **Autosave with conflict detection** | Debounced autosave after 3 seconds; sends revision and shows conflict banner on `409 REVISION_CONFLICT`. | Reduces lost work and protects against concurrent edits. | ⬜ Pending |
| 27 | **Publish** | Toolbar publish calls backend publish; frontend blocks publish when tree validation has errors. Backend validates before activating version. | Promotes a draft into the active runtime view. | ⬜ Pending |
| 28 | **Publish validation** | Server validates JSON payload, required `component_tree`, `page_root`, component code format, duplicate keys, max depth, accessibility label warnings, and placeholder label warnings. | Prevents structurally broken views from going live. | ⬜ Pending |
| 29 | **Version history** | Drawer timeline shows versions, active/draft badges, date/user, selected version, compare, and rollback action. | Provides governance and recovery for view configuration changes. | ⬜ Pending |
| 30 | **Diff support** | Frontend computes visual payload diffs in the history panel; backend has `/diff` API for JSON path changes between versions. | Shows what changed between versions. | ⬜ Pending |
| 31 | **Rollback** | Backend rollback activates a previous version and writes publish log; UI exposes rollback button. | Restores a known-good view version. | ⬜ Pending |
| 32 | **Archive** | List page archive action deactivates active versions and marks the view archived. | Retires a UI view without hard deleting the metadata. | ⬜ Pending |
| 33 | **Import/export/clone/templates** | UI exports current payload as JSON, imports JSON into a new view, clones current view, and saves/loads templates in local storage. Backend also has package export/import endpoints. | Reuses and moves view configurations across environments or views. | ⬜ Pending |
| 34 | **Runtime view APIs** | Published active view can be fetched by artifact ID or by `view_code` with entity and surface. | Allows runtime renderer/apps to load the correct published view. | ⬜ Pending |
| 35 | **Entity schema APIs** | UI Studio can list entity types and fields from stored entity artifacts. | Powers field selection and binding choices. | ⬜ Pending |
| 36 | **Governance read APIs** | APIs exist for variants, events, datasources, diff, export, import, and sync status. Variant/events/datasources currently extract data from latest payload. | Supports governance tooling and future impact analysis around view metadata. | ⬜ Pending |
| 37 | **Plugin management** | Feature-flagged plugin panel and backend routes: list, register, and remove plugins; plugin components can appear in the registry. | Extends UI Studio with custom component libraries when enabled. | ⬜ Pending |
| 38 | **Audit/publish log** | DB table records publish, rollback, archive/import-related actions with user, timestamp, changelog, and tenant. | Provides traceability for UI configuration lifecycle. | ⬜ Pending |
| 39 | **Write-role protection** | Create, import, save draft, publish, validate, rollback, archive, and plugin writes require designer role. | Protects UI Studio modification operations. | ⬜ Pending |
